# Правила агентов HOPE VPN

## Контекст и обязательные ограничения

- Общение и проектная документация — на русском; идентификаторы кода — на английском.
- Работать без BMAD. Не подключать его процессы, роли и шаблоны. Субагентов привлекать только по явному запросу пользователя.
- Публичный кабинет согласован на том же домене, что панель, по пути `/hope/`. Сохранять прежние пути панели/API/подписок. Префикс выводится из SITE_URL; локальная .env остаётся на localhost до разрешённого развёртывания. Пример прокси — `deploy/nginx-hope-location.conf`.
- HOPE VPN — один аккаунт и подписка с двумя интерфейсами: независимый браузерный кабинет (логин/пароль) и Telegram. Telegram необязателен.
- Пользователи переводят деньги владельцу вне приложения. Продление подтверждает владелец вручную. Не внедрять оплату, банковскую сверку или коммерческое автопродление. Явно разрешённый владельцем экстренный час — отдельный временный доступ: только после истечения, раз в 3 часа, максимум 8 запросов за сутки по МСК; он не подтверждает оплату и не снимает блокировки.
- Подключённая 3x-ui — **действующая панель с реальными клиентами**. Локальный запуск приложения не делает панель тестовой.
- По прямому указанию владельца 13.10.2026 чешский сервер работает в production: `PANEL_MODE=real`, `PANEL_WRITES_ENABLED=true`, bot и worker постоянно запущены. Реальные операции выполняются только через штатный кабинет/Telegram flow с ручным подтверждением владельца и сохранением аудита. Не менять поля клиентов/панели для диагностики, не редактировать БД панели напрямую. Локальное `.env` и локальный Docker остаются write-off; развёртывание не означает разрешения на искусственные тестовые операции или рассылки.
- Не менять UUID, subId, квоты, привязки, транспорты, маршрутизацию и прочие поля ради диагностики. Не редактировать БД панели напрямую.
- Утверждены тарифы: 7 дней 99 ₽, 1/3/6/12 месяцев 299/799/1499/2799 ₽. Реквизиты администратор всегда присылает лично; не автоматизировать их отправку. «Я оплатил» — заявление клиента, не подтверждение денег. Paid и готовый VPN — разные состояния.
- Новая покупка через бот может предшествовать браузерному аккаунту. Только ручная выдача создаёт новую подписку/аккаунт с Telegram; не присваивать старую запись панели покупателю. Собственные логин/пароль задаются по одноразовой onboard-ссылке, затем сохраняются коды восстановления.
- Для iPhone/iPad с российским App Store предлагать INCY первым, сохраняя Happ для уже установивших его. Официальные ссылки/схемы — `core/clients.py`; совместимость настоящего туннеля не объявлять по проверке URL.
- Импорт не доказывает владение подпиской. Приглашение передаёт администратор по проверенному прежнему контакту. К существующему аккаунту Telegram привязывается после подтверждения в боте и исходной браузерной сессии; `tgId` панели не записывается.
- Кнопка существующей подписки создаёт одну открытую binding-заявку без текста клиента; группа получает Telegram-профиль/ID, владение всё равно проверяется вручную. Notice.admin_event направляется в ADMIN_GROUP_CHAT_ID с fallback ADMIN_CHAT_ID (текущий ID группы); личные уведомления/секреты туда не зеркалировать.
- Не отправлять реальные сообщения пользователям/администратору в тестах. Использовать имитацию Telegram API.

Native без `DATABASE_URL` использует отдельную SQLite. Всегда выяснять целевую БД перед командами; не подменять тестовую базу рабочей. Эти сведения — снимок, актуальное окружение проверять без вывода секретов.

## Документация: Specification-Driven Development (SDD)

SDD здесь означает разработку от явной спецификации, без отдельного фреймворка. Входная точка — [docs/sdd/README.md](docs/sdd/README.md); текущая базовая спецификация — [docs/sdd/SPEC.md](docs/sdd/SPEC.md).

Для каждого содержательного изменения поведения, модели данных, API, безопасности или эксплуатации:

1. До реализации прочитать относящиеся требования и создать/обновить `docs/sdd/changes/NNNN-short-name.md` по [шаблону](docs/sdd/templates/change.md). Указать проблему, границы, требования, проверяемые критерии, риски и вопросы. Не требовать отдельного согласования документа, если работа уже разрешена пользователем; фиксировать разумные предположения.
2. Во время работы обновлять статус и решения при изменении объёма. Для значимого архитектурного решения создать `docs/sdd/decisions/NNNN-short-name.md`: контекст, решение, последствия, альтернативы и ссылки. Не выдавать предположение за проверенный факт.
3. Вместе с кодом обновить базовую SPEC, затронутые `docs/product.md`, `docs/architecture.md`, `docs/launch.md`, `docs/operations.md` и README. Редактировать только относящиеся разделы; не копировать одно требование во все документы.
4. До завершения записать фактические проверки и ограничения в спецификации изменения, связать требования → код → тесты/ручные проверки. Сетевое исследование или развёртывание дополнительно отражать в `docs/research/YYYY-MM-DD.md`.
5. Для изменения кнопки/действия обновить соответствующий файл в docs/use-cases/, индекс и INVENTORY; новые действия получают следующий стабильный UC-ID своей группы B/W/A. Не переиспользовать ID и не выдавать критерии приёмки за выполненные тесты.
6. Добавить изменение в индекс SDD. Статус `verified` означает выполнение критериев в указанной среде; непроверенное поведение отмечать явно. Не объявлять готовность production по результатам demo/API.

Мелкие опечатки и форматирование не требуют отдельной спецификации: исправить документ непосредственно. Документация ведётся **в каждой соответствующей задаче**, а не только по просьбе пользователя и не через неподтверждённую фоновую автоматизацию. Изменение не завершено, пока документация расходится с ним. Исторические отчёты сохраняют результаты своего запуска; текущие требования обновляются в SPEC.

## Правила реализации

- Держать бизнес-правила общими для web/bot; избегать ненужных SPA, микросервисов и инфраструктуры.
- Сохранять абсолютный целевой срок и идемпотентность; блокировки/версии защищают от повторного и конкурентного продления. Календарные месяцы считаются в МСК, данные времени хранятся в UTC.
- После таймаута записи сначала сверять фактическое состояние; не повторять запись вслепую. Partial/conflict приостанавливают новые записи. Сбой Telegram не откатывает срок.
- Сохранять различие между коммерческим сроком, enable, квотой и фактическим применением. HTTP 200, node-sync и рабочий VPN-туннель — разные уровни проверки.
- Использовать штатные миграции; не удалять локальные базы/volumes и не перезаписывать бэкапы ради удобства. Восстановление проверять только изолированно.
- Не читать/печатать `.env` целиком. Проверять наличие и корректность нужных параметров с маскированием. Секреты, персональные конфиги, приглашения, QR и реальные выгрузки не включать в Git, логи, скриншоты или документацию.
- Все поддерживаемые пользовательские настройки документировать в одном .env.example; реальные значения — только .env. При добавлении параметра обновлять шаблон и operations; учитывать приоритет окружения процесса и Docker DATABASE_URL.
- `DATA_ENCRYPTION_KEY` не менять без миграции защищённых данных. `.env`/бэкапы — 0600; `data/` и `artifacts/` игнорируются. `.env.example` содержит только безопасные примеры.
- Для изменений зависимостей синхронизировать lock/export и образы. Контракт внешнего API проверять по первичным источникам и ответам сервера, не по памяти.

## Проверки и завершение

Обычные команды: `uv run ruff check .`, `uv run python manage.py check`, `uv run pytest -q`. При изменении моделей: `uv run python manage.py makemigrations --check --dry-run`. Выбирать тесты по затронутому риску; для документации достаточно проверки ссылок/согласованности, запуск приложения не нужен.

Конкурентность и PostgreSQL-специфику проверять на отдельной тестовой PostgreSQL. Browser smoke разрешён только в изолированном demo+DEBUG окружении; действующие bot/worker не должны доставлять его искусственные Telegram ID. Не запускать smoke на текущей real-интеграции. Команды эксплуатации — [docs/operations.md](docs/operations.md).

В итоговом сообщении указать результат, проверки, изменённые документы и существенные оставшиеся ограничения. Не утверждать прохождение проверок, которые не выполнялись. Не создавать коммиты, публикации или автоматизации без запроса пользователя.
