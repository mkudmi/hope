# Настройка и обслуживание

## Окружение

Все поддерживаемые настройки бота, кабинета, worker, панели, тарифов, БД и локальных проверок описаны по разделам в едином `.env.example`. Рабочие значения вносятся в `.env`; отдельных файлов для бота и web не нужно. `.env.example` — шаблон, второй источник настроек не создаётся.

`.env` имеет права 0600, не входит в Git или образ Docker. `DJANGO_SECRET_KEY` защищает приложение, `DATA_ENCRYPTION_KEY` — снимки панели/бэкапы. Замена ключа шифрования требует отдельной миграции защищённых данных. Секреты и персональные конфигурации в отчётах не печатать.

Docker: web, worker, db и bot с профилем `telegram`. Порты HTTP8000 и PostgreSQL15432 доступны только на loopback. `APP_DATABASE_NAME` выбирает БД приложения: `hope_live` — отдельная БД HOPE Czech production (локально тот же label остаётся write-off), `hope` — сохранённая демонстрация. Данные панели хранятся на прежнем сервере, её БД приложение не использует.

На чистом компьютере сначала запустите Docker Desktop и проверьте наличие прежних
контейнеров/volumes HOPE. Не генерируйте новые ключи шифрования или пароль БД,
если данные уже существуют. `scripts/init_env.py` работает только при отсутствии
`.env`; существующий файл дополните недостающими значениями, сохранив секреты.
На Windows ограничьте ACL файла текущим пользователем (эквивалент private 0600).

PostgreSQL в Compose первоначально создаёт базу `hope`. Если выбрана отдельная
`APP_DATABASE_NAME=hope_live`, на новом volume перед запуском web создайте её:

```sh
docker compose up -d db
docker compose exec db createdb -U hope hope_live
docker compose --profile telegram up -d --build web worker bot
docker compose exec web python manage.py bootstrap_owner
docker compose exec web python manage.py check
docker compose ps
```

`createdb` требуется только для отсутствующей базы; существующую не пересоздавать.
Миграции запускает web. Чистая база не содержит импортированных подписок: запуск
бота не переносит их автоматически. Проверяйте имя бота через getMe: оно должно
совпадать с BOT_USERNAME. Локальный запуск 12.10.2026 на текущем компьютере описан
в [SDD 0010](sdd/changes/0010-local-bot-deployment.md); прежние результаты импорта
в отчётах относятся к прежнему окружению.

`docker compose down` сохраняет базы; `down -v` удаляет локальный volume и не нужен для обычной остановки.

При первом входе владельца откройте Google Authenticator или другое TOTP-приложение: «+» → «Сканировать QR-код» на странице настройки → введите текущие 6 цифр → «Подключить защиту и войти». На одном телефоне можно раскрыть запасной ручной ключ, скопировать его и добавить аккаунт по ключу с типом «По времени». Сохраните ключ в защищённом месте. QR доступен только в текущей сессии первоначальной настройки; после подключения он закрывается. Следующие входы требуют только кода, повторно сканировать QR не нужно. Восстановление владельца из доверенной консоли:

```sh
docker compose exec web python manage.py reset_staff_mfa --username admin --confirm-reset
docker compose exec web python manage.py changepassword admin
```

Сброс MFA завершает прежние сессии. `bootstrap_owner` создаёт отсутствующего локального владельца по `LOCAL_ADMIN_*`, не меняет пароль существующего и не обращается к панели. Для production используйте `createsuperuser` только по явному поручению владельца; не передавайте пароль аргументом команды и не записывайте его в логи. Production login `admin` создан 2026-10-13 с согласованными владельцем локальными credentials. Откройте `https://<домен-панели>/hope/staff/` и при первом входе завершите обязательную настройку TOTP. Сверка provisioning описана в [SDD 0019](sdd/changes/0019-czech-owner-account.md).

## Telegram

Навигация по inline-кнопкам редактирует сообщение, кнопку которого нажали.
Команды, текстовая поддержка и уведомления создают отдельные сообщения.
Старую историю бот не удаляет. После обновления core/bot.py достаточно
пересобрать и пересоздать только bot: `docker compose --profile telegram up -d --build --no-deps bot`.

Username — `BOT_USERNAME`, токен — `BOT_TOKEN`. Проверены токен и имя @hope2vpnbot, webhook отсутствует. Перед polling сервис сам проверяет это соответствие. Существующий webhook не удаляется и ожидающие updates не сбрасываются автоматически.

Страница привязки Telegram в кабинете сначала открывает `tg://resolve` для установленного приложения. Если браузер не передал диплинк, используйте HTTPS fallback «откройте ссылку через Telegram»; оба перехода несут один короткоживущий токен.

Бот работает в личных чатах; Start не создаёт VPN-доступ. Telegram ID сохраняется в собственной базе HOPE, поле `tgId` 3x-ui ради привязки не записывается. Потеря/блокировка Telegram не закрывает кабинет.

`ADMIN_GROUP_CHAT_ID` — числовой ID админской группы (обычно отрицательный), бот должен быть её участником и иметь право писать. Если параметр пустой, административные события используют `ADMIN_CHAT_ID`; текущий ADMIN_CHAT_ID уже содержит ID существующей группы. События помечаются admin_event отдельно от личных сообщений. Заявки/поддержка, заказы/отмена/заявление об оплате/ручное решение, очередь/подтверждение/ошибка операций, приглашения (без самой ссылки), активация аккаунта, Telegram-привязка и итог импорта поступают через durable outbox с retry/429/403. Без доставки данные остаются в админке. Приглашения, recovery/onboard и VPN-ссылки, пароли и текст обращения/реквизитов в общие события не копируются; заявка на привязку содержит только Telegram-профиль и ID. Подписочные сообщения требуют подтверждённой привязки. Ответы на созданные клиентом заказы/обращения могут доставляться BotContact до регистрации; VPN-секреты в такие уведомления не включаются. Sent означает приём Telegram, а не прочтение.

Адрес `127.0.0.1` открывается только на текущем компьютере; для телефона укажите доступный ему адрес, `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS`. Для публичного доступа нужен HTTPS. Публикация через внешний туннель не выполняется автоматически.

## Действующая панель

`PANEL_URL` — адрес перед UI-окончанием `/panel/`. Адаптер сам добавляет `panel/api/...`. Подтверждённую ошибку окончания исправили в `.env`; предыдущая конфигурация сохранена локально в `data` с правами 0600.

`PANEL_API_TOKEN` — API-токен без слова Bearer. `PANEL_SUB_URL` — общий HTTPS адрес выдачи, без персонального subId; он получен из настроек панели. `PANEL_INBOUND_IDS` — согласованный набор рабочих транспортов, AUTO TEST не включён по умолчанию. `PANEL_EXCLUDED_CLIENTS` — точные метки gateway/служебных/диагностических записей. Пока исключения не перечислены: перед приглашениями владелец должен разобрать записи и исключить служебные в карточке.

Локальная конфигурация остаётся с `PANEL_WRITES_ENABLED=false`. По прямому указанию владельца 13.10.2026 Czech production работает с `PANEL_MODE=real` и `PANEL_WRITES_ENABLED=true`. Worker применяет только штатные операции, созданные и подтверждённые владельцем в приложении; перед запуском он останавливается, если в серверной БД есть queued/applying операции. Не использовать действующие подписки для искусственных сценариев и не менять панельные поля ради диагностики. Политика запуска: [SDD 0017](sdd/changes/0017-czech-production.md).

Read-only импорт:

```sh
docker compose exec web python manage.py import_panel
```

Каждый существующий клиент сначала unmanaged и без владельца. По прежнему проверенному контакту передайте приглашение, после активации человек сам подключит Telegram. Служебные записи не превращать в клиентов. Общие subId требуют ручного разбора. Смена идентичности не принимается автоматически.

Адаптер сопоставлен с API/исходниками v3.9.0 и текущей карточкой сервера: get возвращает `{client,inboundIds,usedTraffic}`; числовой `client.id` — ID записи, а `uuid` преобразуется в строковый `id` update. Вложенный JSON нормализуется, остальные поля сохраняются. `obj.nodePending` не считается полным применением.

Источники: [clients API](https://github.com/MHSanaei/3x-ui/blob/v3.9.0/docs/content/docs/en/reference/api/clients.mdx), [контроллер](https://github.com/MHSanaei/3x-ui/blob/v3.9.0/internal/web/controller/client.go), [nodePending](https://github.com/MHSanaei/3x-ui/blob/v3.9.0/internal/web/controller/util.go).

## Выдача и продление

Новый клиент: черновик → приглашение → регистрация → «Создать VPN-доступ». Начальная длительность фиксируется при первой выдаче, чтобы очередь/регистрация не расходовали её заранее. При длительном неполном применении компенсацию владелец назначает явным исправлением даты с причиной.

Старый клиент: импорт → проверка владельца → приглашение. Для панельных изменений дополнительно «Принять под управление». Панельный перенос срока `reset/resetDay/resetWeekday` должен быть выключен; HOPE не отключит его скрытно.

Продление: владелец проверяет перевод вне системы, выбирает срок/причину, видит старую/новую дату и подтверждает. Сервис сохраняет абсолютный срок один раз; повторный POST его не удваивает. Сроки в UTC, календарные месяцы и отображение в МСК. Трафик/квоты/ключи не сбрасываются; включение доступа — отдельный явный выбор.

Worker сохраняет намерение до записи, затем сверяет клиента, каждый инбаунд, master core и свежесть/состояние нод. Это не тест пользовательского туннеля. API-проверка не обещает отсутствие перерывов: в research зафиксирован перезапуск Xray на Сербии при hot-apply.

Перед включением записи необходимы относящийся бэкап, отдельный тестовый клиент, оценка node-sync и трафиковая проверка. Не экспериментировать с действующими клиентами и не перезапускать рабочие службы ради диагностики.

## Ошибки и пауза

Partial/conflict останавливают новые записи глобально. «Повторить проверку» после записи только сверяет результат; не переигрывает прибавление срока. При неполном результате разберитесь с панелью, примите её действующее состояние и создайте новое явное действие, если необходимо. Изменение срока через UI панели не перезаписывается молча.

```sh
docker compose exec web python manage.py panel_writes pause
docker compose exec web python manage.py panel_writes resume
```

Resume требует разрешённых конфликтов и не отменяет `.env`-флаг. Десятиминутная аренда worker может задержать возврат очереди после аварийной остановки. Сверка обновляет по одной устаревшей управляемой записи за цикл; при недоступности API остаётся прежний timestamp.

## Резервные копии

```sh
docker compose exec web python manage.py backup_hope --output /app/data/hope-backup.enc
docker compose cp web:/app/data/hope-backup.enc ./data/hope-backup.enc
```

Копия зашифрована, права 0600; существующий файл не перезаписывается. Для следующих копий задайте другое имя. Выгрузите её с контейнера на отдельное хранилище: `/app/data` не является постоянным backup-volume. `DATA_ENCRYPTION_KEY` сохраните отдельно, без него восстановление невозможно.

В пустой мигрированной БД с прежним ключом:

```sh
python manage.py restore_hope --input <backup.enc> --confirm-restoration
```

После восстановления токены/сессии отзываются, PostgreSQL sequences восстанавливаются, управляемые записи требуют сверки, запись приостановлена. Старые queued-команды не отправляются поверх новых реальных продлений. Round-trip восстановления проверен на SQLite/PostgreSQL.

## Проверки и ограничения

`uv run pytest -q`, `uv run ruff check .`, `uv run python manage.py check`. Конкурентная блокировка проверяется только PostgreSQL. Browser smoke требует отдельного demo+DEBUG окружения и непривязанного `existing-client`. Если BOT_TOKEN заполнен, worker/bot должны быть остановлены на время теста: используются искусственные Telegram ID. Скрипт не разрешён в real-режиме.

Для публичного запуска понадобятся HTTPS, реальные домены, `DEBUG=false`, PostgreSQL, защищённый канал к API и offsite-бэкапы. Доступность кабинета без VPN на телефоне/операторах и прекращение реального туннеля после истечения должны проверяться отдельно. Локальный запуск этого не подтверждает.

## Экстренный доступ

Кнопка находится в `/cabinet/`. Нужны: привязанный владелец, управляемый существующий клиент, фиксированный истёкший срок, verified-состояние, включённый технический клиент и свободная квота. Изменение только expiryTime; блокировки, секреты и счётчики не меняются. Административный запрет и техническое отключение пользователь самостоятельно не снимает.

Экстренный час отсчитывается от принятия запроса. Интервал 3 часа, предел 8 принятых запросов за сутки МСК относятся к подписке. Даже failed/partial принятая операция остаётся в лимите. Незавершённый/ошибочный результат требует разбора владельцем, а не нового слепого запроса. Если очередь задержалась до окончания часа, запись не производится. История/сообщения показывают результат сверки.

На Czech production флаг записи включён, поэтому экстренная операция доступна только при выполнении всех условий выше, штатном подтверждении владельца и отсутствии глобальной паузы. Локальный write-off окружения её не применяет.

## Кабинет на домене панели: /hope/

Владелец подтвердил общий домен и путь `/hope/`. Адрес кабинета: `https://<домен-панели>/hope/`; существующие адреса панели/API/подписок сохраняются. Czech production проксирует путь действующим Caddy на loopback web-порт 18000. Локальная `.env` остаётся на localhost.

Пример production-параметров (подставить домен, без секретов в документах):

```dotenv
DEBUG=false
SITE_URL=https://vpn.example.com/hope
ALLOWED_HOSTS=vpn.example.com
CSRF_TRUSTED_ORIGINS=https://vpn.example.com
TRUST_PROXY_HTTPS=true
PANEL_WRITES_ENABLED=true
```

Эта production-конфигурация относится только к Czech deployment; локальную
`.env` и Docker оставить с `PANEL_WRITES_ENABLED=false`.

Путь из SITE_URL задаёт FORCE_SCRIPT_NAME, `/hope/static/` и область cookies `/hope/`. CSRF_TRUSTED_ORIGINS содержит только origin, без `/hope/`. Имена cookies — hope_session и hope_csrf; после изменения имён ранее открытые сессии потребуют повторного входа. SITE_URL, PANEL_URL и PANEL_SUB_URL — разные настройки; не дописывать `/hope/` к адресам панели или выдачи конфигураций.

На Czech production Caddyfile `/opt/3x-ui-proxy/Caddyfile` содержит HTTPS-маршруты панели, подписок, транспортов и HOPE auto gateway. Маршрут кабинета добавлен 2026-10-13: `/hope` → `/hope/`, обработчик `/hope/*` снимает prefix перед upstream `127.0.0.1:18000`; Django восстанавливает публичный префикс при построении адресов. Админка HOPE доступна по `/hope/staff/` и требует входа. При будущих изменениях проверить matcher-конфликты, сохранить файл и inode, изменить конфигурацию на месте, выполнить `docker exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`, затем graceful reload через admin API Caddy на loopback. Не перезапускать контейнер Caddy и службы панели/VPN. HTTPS login и `/hope/static/app.css`/`app.js` проверены (200), а staff перенаправляется на login; проверка CSRF и активной browser-сессии остаётся отдельной. Результаты публикации — [SDD 0018](sdd/changes/0018-publish-hope-cabinet.md). Nginx-фрагмент остаётся примером для других размещений.

TRUST_PROXY_HTTPS разрешено только при недоступном извне upstream и прокси, который перезаписывает X-Forwarded-Proto собственным `$scheme`. Пример настроен на loopback 127.0.0.1:8000. Контейнерный health-check отправляет HTTPS-заголовок для внутреннего запроса при таком размещении. HTTP→HTTPS на публичном сервере и сертификаты обслуживаются существующим прокси.

Пути и cookies предотвращают обычные коллизии, но панель и кабинет остаются одним браузерным origin: это не изоляция разных доменов. При реальном размещении проверить вход/CSRF/logout, static, QR, приглашения, сообщения бота и сохранность всех прежних маршрутов панели/подписок. Доступность общего домена без VPN также проверяется отдельно: совместный домен сам по себе её не обеспечивает.

## Полноценный бот и ручные заказы

Команды: /start, /prices, /buy, /renew, /orders, /status, /support, /account, /help, /recover. После обновления отправить /start заново: уже отправленный приветственный текст не меняется автоматически, прежние кнопки обрабатываются новым кодом. Поддержка принимает текст в следующем сообщении; /start или «Отменить ввод» завершает режим обращения.

Каталог включается TARIFFS_APPROVED=true; цены в целых рублях задают TARIFF_WEEK_PRICE, TARIFF_MONTH_PRICE, TARIFF_QUARTER_PRICE, TARIFF_HALFYEAR_PRICE, TARIFF_YEAR_PRICE. Текущая .env содержит утверждённые 99/299/799/1499/2799 ₽. Пересоздание контейнеров необходимо при изменении окружения. Неподтверждённый каталог скрыт. Заказ хранит принятую цену/срок; изменение каталога не переоценивает его.

Заказы: `/staff/orders/`. В карточке владелец лично связывается с клиентом и присылает реквизиты своим каналом. Затем сверяет поступление перевода, указывает основание и подтверждает проверку. Кнопка «Я оплатил» только переводит заказ в payment_review, а не создаёт доступ. После paid отдельно открыть предпросмотр выдачи и подтвердить: для нового доступа выбрать квоту/HWID, для продления явно решить вопрос включения. После verified заказа клиент получает уведомление. Failed/partial/conflict разбираются через карточку операции, оплачивать повторно не требуется.

Новая выдача создаёт новую подписку/Telegram-аккаунт с unusable password. Старый импортированный клиент к такому заказу не прикрепляется. Продление Telegram-заказа требует прежней действующей привязки и версии подписки; web renewal проверяет владельца браузерного аккаунта без обязательного Telegram. В Czech production ручное подтверждение заказа разрешает штатное применение через очередь; `paid` само по себе доступ не создаёт. Не создавать фиктивные заказы или платежи для проверки.

Новому Telegram-клиенту команда `/account` выдаёт одноразовый onboard-token на 15 минут. Он задаёт выбранный логин/пароль и сохраняет восемь кодов восстановления. На главном экране оставлена одна URL-кнопка «Открыть сайт ↗»; при уже открытом чужом/административном аккаунте нужно выйти или открыть приватное окно. Ссылку не пересылать. После настройки работает обычное восстановление; `/recover` до настройки направляет в onboarding.

Для iPhone/iPad сначала предлагается INCY ([App Store RU](https://apps.apple.com/ru/app/incy/id6756943388)); установленный Happ можно сохранить. Другие версии — [incy.cc](https://incy.cc/), Happ — [happ.info](https://happ.info/). В кабинете incy://import/ и happ://add/; при проблеме перехода вручную добавить ту же личную ссылку. [Схема INCY](https://docs.incy.cc/deep-links/) проверена по документации, но реальный импорт/туннель на телефонах остаётся проверкой перед публичным запуском.

Перед миграцией 0004 сохранён backup собственной базы в data/hope-before-purchases.enc, 0600. Панельная БД не мигрируется. Backup/restore новых контактов/заказов/outbox проверен в тестовой БД; старые контейнеры нельзя запускать поверх обновлённой схемы без оценки совместимости. Откат интерфейса предпочтительнее удаления записей клиентов/заказов.

## Комментарии панели в списке клиентов

Административная таблица и карточка показывают comment 3x-ui отдельным полем «Комментарий из панели». Поиск учитывает этот текст. Для обновления нажмите «Импортировать из панели» или выполните import_panel; импорт только читает панель. Пустой/удалённый комментарий отображается тире, локальная метка клиента сохраняется. Успешное чтение принятого состояния также обновляет поле. Конфликтные и исключённые записи сохраняют прежние проверки/правила импорта; комментарий не доказывает владение подпиской. Это приватная административная информация, в кабинете пользователя и Telegram она не показывается.

## Привязка существующего доступа через заявку

Нажатие «Существующая подписка» в личном чате создаёт одно открытое binding-обращение и уведомляет группу с username, именем/фамилией (если есть), Telegram ID и ссылкой на контакт. Повторное нажатие показывает ожидание без новой заявки. Пользователь не пишет сообщение. В «Обращениях» проверьте владельца по прежнему контакту, найдите подписку по комментарию/метке и выдайте приглашение лично. Ответ в обращении приходит пользователю и закрывает заявку; сам по себе ответ не связывает подписку. Для уже связанного активного аккаунта новая заявка не создаётся.

## Справочник действий интерфейса

Перед ручной проверкой сценария используйте [UC соответствующей кнопки](use-cases/README.md). Ошибки и текущие ограничения записаны в каждом сценарии; критерии приёмки не означают, что все действия разрешено выполнять на рабочей панели.

### Применение настроек из .env

Экспортированные переменные процесса имеют приоритет над файлом. Docker задаёт DATABASE_URL для web/worker/bot из LOCAL_DB_PASSWORD и APP_DATABASE_NAME, поэтому строка DATABASE_URL файла относится к native-запуску. После изменения значений пересоздайте нужные локальные сервисы: `docker compose --profile telegram up -d --force-recreate web worker bot`. Изменение LOCAL_ADMIN_PASSWORD не меняет пароль существующего владельца; используйте changepassword. При публичном запуске выставьте DEBUG=false и SECURE_SSL_REDIRECT=true вместе с HTTPS/proxy. BROWSER_BASE_URL относится только к изолированному demo smoke. Адреса официальных приложений и внутренние ограничения безопасности остаются в коде, не являются поддерживаемыми env-параметрами.

Возврат «Главное меню» в Telegram показывает тот же экран, что /start: приветствие
без привязки либо меню связанного аккаунта. Состояние связи проверяется заново;
при проверке нажмите /start → тарифы → главное меню и сравните текст и кнопки.
См. [SDD 0012](sdd/changes/0012-bot-home-screen.md).

## Сервер Чехии и GitHub Actions

Раскатка HOPE — [deploy/README](../deploy/README.md), отдельный project hope-cz,
серверная .env /opt/hope/shared/.env (0600). Production deploy запускается вручную
из GitHub Actions после Linux/Python 3.12/PostgreSQL тестов и оставляет web, bot и
worker работающими. Перед cutover остановить локальные bot/worker с тем же токеном.
Web слушает loopback 18000; публичный Caddy проксирует кабинет по `/hope/`.
Первоначальное создание production-владельца остаётся отдельным шагом.
Секреты приложения на сервере; SSH deploy key и закреплённый host key хранятся в
существующем GitHub environment `czech-standby`. Не удалять volumes.

### Доверенный браузер MFA

Флажок на MFA-входе по желанию пропускает повторный TOTP в этом браузере на 15 дней; повторная аутентификация паролем сохраняется. Смена пароля или отзыв авторизации инвалидируют запись. Схему БД обновляет штатная миграция `0007_trusted_browser`; управлять доверенными браузерами вручную не требуется. Подробности: [SDD 0023](sdd/changes/0023-trusted-browser-15-days.md).

### Импорт после входа администратора

После каждого нового входа и проверки MFA приложение один раз выполняет штатный
импорт панели. Вход может занять время чтения API; на каждом обновлении страницы
импорт не повторяется. При ошибке появляется сообщение, вход сохраняется;
повторить попытку можно ручной кнопкой. Импорт читает панель и сохраняет локальные
снимки, аудит и уведомление группы, поэтому каждый новый вход даёт итог импорта.
Новых переменных окружения и миграций для автоимпорта нет. Статус выкладки —
[SDD 0024](sdd/changes/0024-auto-import-on-admin-login.md).

### Ссылка Telegram-профиля в заявках

Новые binding-уведомления содержат кликабельный «Открыть профиль». При username
используется HTTPS `t.me`, без него — оформленный Telegram ID; приватность
пользователя может ограничить переход. Ответить можно через обращение в кабинете.
Для метаданных ссылки требуется штатная миграция `0008_notice_telegram_entities`;
новых настроек нет. Старые отправленные уведомления не редактируются. Статус
выкладки и проверок — [SDD 0025](sdd/changes/0025-telegram-contact-link.md).

### Доставка меню после привязки

После финального подтверждения в исходном браузере worker доставляет личное
сообщение с главным меню аккаунта. Нажимать `/start` ещё раз не требуется.
Задержка соответствует обычной очереди Notice; временные ошибки используют
существующий retry. Отвязка до доставки отменяет меню. Для флага нужна штатная
миграция `0009_notice_telegram_account_menu`, дополнительных настроек нет.
Статус подготовки и ограничения — [SDD 0026](sdd/changes/0026-menu-after-telegram-binding.md).

### Продление из кабинета и обработка заказов в Telegram

Веб-клиент выбирает срок в /renewal/, читает ручные реквизиты и статусы в /orders/.
Карточка обновляется автоматически при изменении сообщений/статуса; кнопка
«Обновить заказ» остаётся запасным вариантом. «Я оплатил» не подтверждает деньги.

Для операторов явно задайте ADMIN_TELEGRAM_USER_IDS — личные положительные ID
через запятую, без username; пустой список запрещает чатовые действия.
ADMIN_TELEGRAM_LOGIN — существующий активный staff логин (пример admin) для
аудита. Пример параметров только в .env.example; реальные значения хранить в .env.
Действия принимаются только в ADMIN_GROUP_CHAT_ID, fallback ADMIN_CHAT_ID.
Текстовые ответы отправлять от личного профиля: sender_chat/анонимный отправитель
отклоняются. Callback проверяет фактический личный ID, который передаёт Telegram. Клиентскую TelegramIdentity административному аккаунту не создают.

Ответьте текстом (до 2000 символов) на доставленное уведомление бота о заказе:
оно связано с заказом по chat_id/message_id. Клиент прочитает ответ в кабинете,
а при наличии своего Telegram получит его лично. Профиль/forwarded-текст не
используются как идентификатор заказа. Общий чат не получает зеркальную копию
переписки. Для privacy-mode достаточно ответа на сообщение бота —
[официальный Telegram FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

Для renewal нажмите «Проверить перевод и продлить», сверяйте сумму/подписку/срок,
затем «Перевод проверен — продлить». Альтернатива — карточка заказа в staff,
ручная проверка с основанием и такой же финальный предпросмотр. Он истекает
через 10 минут и связан с конкретным оператором и каналом. После изменений
версии/владельца/условий нужен новый предпросмотр. Write-off и конфликты не обходятся;
paid/provisioning не означают готовый туннель. Сбои применения разбираются штатно,
без повторной слепой записи.

Нужна штатная миграция 0010_web_renewal_and_admin_orders. Перед каждой выкладкой
проверить отсутствие нескольких активных PurchaseOrder для одного user: новая
уникальность не должна отменять реальные заказы автоматически. Данные старых
Telegram заказов сохраняются; прежние Notice-ответы остаются в уведомлениях,
новая переписка хранится в OrderMessage. Сетевой сбой sendMessage может создать
повтор сообщения, как прежде; отвечать нужно на последнее доставленное
уведомление с сохранённым message_id. Выложено на Czech production 13.10.2026, миграции 0007–0010 применены,
allowlist владельца настроен (локальная .env без изменений):
[0027](sdd/changes/0027-web-renewal-and-telegram-admin.md).

Восстановление зашифрованного backup дополнительно истекает все неиспользованные OrderApproval, чтобы старый предпросмотр не подтвердил оплату после восстановления.
