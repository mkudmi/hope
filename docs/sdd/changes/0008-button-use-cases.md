# 0008 — Use cases кнопок

Статус: verified. Дата: 2026-10-12. Требование R-12.

Цель: для каждого пользовательского действия по кнопке бота, кабинета и административного интерфейса создать отдельный Markdown UC. Включаются ссылки-кнопки, навигация, раскрывающиеся блоки и динамические варианты (тарифы, устройства, приложения, состояния переключателей). Повторяющиеся кнопки одинакового действия могут ссылаться на один UC с перечислением мест и подписей; разные действия/контексты имеют отдельные UC.

Критерии: единый индекс; стабильные UC-ID; актор, триггер/источник кода, предусловия, основной сценарий, альтернативы/ошибки, постусловия и побочные эффекты, критерии приёмки; сверка с текущей реализацией без выдуманной автоматизации. Все пути/относительные ссылки проверены. Реальные секреты и профили не включать. Описанные проверки — сценарии приёмки, а не утверждение о новых выполненных продуктовых тестах.

Границы: только документация, без изменения приложения/БД/панели/рассылок/развёртывания. Текущий live write-off фиксируется как ограничение соответствующих UC; будущий /hope/ не выдается за запущенный адрес.

## Результат и проверка

Созданы 133 отдельных UC: 47 bot, 37 web, 49 admin. README содержит полный индекс, INVENTORY связывает все 95 вхождений button/a/summary в текущих 21 HTML-шаблонах и маршруты/динамические варианты Telegram. Universal form.html раскрыт на конкретные формы, disabled/active состояния экстренной кнопки используют тот же UC. Повторяющиеся навигационные кнопки с одинаковым эффектом используют один сценарий.

Локальная проверка документов: число элементов каждого шаблона совпадает с числом связей, каждый UC имеет все обязательные разделы и уникальный ID, исходные пути существуют, 854 относительные ссылки внутри каталога UC и ссылки в обновлённых входных документах проверены. Отдельно сверены сроки токенов, callback/url/copy_text, отмена только awaiting_payment, текущий write-off и нюансы повторной обработки/переключателей/рассылки. Продуктовые тесты не запускались: задача меняет только документацию. Приложение, секреты, базы, панель и рассылки не изменены; развёртывание не выполнялось.

Наблюдения по коду явно отражены в UC, не исправлялись этой задачей: обращение без reply_id может повторно уведомить при повторном POST; переключатель на повтор переключает обратно; stage=prepared при повторной обработке может выполнить первую разрешённую запись; список предпросмотра рассылки может показывать исходный queryset сверх 500 зафиксированных ID.
