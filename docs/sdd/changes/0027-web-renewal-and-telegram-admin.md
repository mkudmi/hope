# 0027 — Заказ продления в кабинете и ручная обработка из Telegram

Статус: verified (изолированно; не развёрнуто). Создано: 2026-10-13. Обновлено: 2026-10-13.
Требования: R-01, R-05, R-06, R-08, R-15. Решение: ADR 0005.

## Проблема и результат

Веб-продление сейчас является текстовым обращением. Пользователь должен выбрать
срок/цену, получить вручную написанные реквизиты в этом же кабинете, сообщить об
оплате и дождаться ручного подтверждения владельца из Telegram или веба.

## Объём и требования

- Использовать общий PurchaseOrder для web и Telegram; Telegram необязателен.
  Карточка автоматически обновляется при изменении ответа/статуса (10 секунд, только видимая вкладка; GET updates не отдаёт текст переписки). Веб-заказ всегда относится к существующей собственной подписке; новая выдача
  и назначение чужого панельного клиента не входят в этот сценарий.
- Веб показывает все утверждённые сроки 7 дней/1/3/6/12 месяцев; бот сохраняет
  временно скрытые 6/12 месяцев. Цена/срок фиксируются в заказе, изменившийся
  каталог отклоняет устаревшее предложение. Один активный заказ на аккаунт.
- В кабинете есть карточка/список собственных заказов, сообщения администратора,
  «Я оплатил» и отмена до сообщения о переводе. Чужие заказы недоступны.
- Админка и группа получают заказ. Администратор отвечает текстом на уведомление
  бота; сообщение связывается по сохранённым chat_id/message_id, не по тексту.
  Ответ сохраняется в заказе и доставляется лично при наличии Telegram. Никакой
  автоматической отправки реквизитов и банковской сверки нет.
- Административные действия Telegram доступны только ADMIN_TELEGRAM_USER_IDS
  в настроенном ADMIN_GROUP_CHAT_ID (fallback ADMIN_CHAT_ID). Username/членство
  в группе не дают права. Используется активный staff аккаунт ADMIN_TELEGRAM_LOGIN;
  числовой отправитель записывается в аудит. Пустой allowlist запрещает действия.
- Из чата/веба: предпросмотр конкретного заказа, суммы, текущего и целевого срока;
  затем явное подтверждение ручной проверки перевода и продления. Предпросмотр
  живёт 10 минут, связан с администратором/Telegram ID, состоянием заказа и
  версией подписки. Нельзя переключить канал подтверждения или применить чужой
  предпросмотр. Повторная кнопка не продлевает второй раз.
- Подтверждение оплаты и постановка renewal в очередь атомарны. Ошибка prepare
  откатывает оплату в этом совмещённом действии. Использовать штатные блокировки,
  operation_id=order.id, абсолютный срок, сохранение VPN-полей и проверку worker.
  Paid/provisioning/verified различаются; «Я оплатил» не меняет срок.
- История переписки не зеркалируется в админскую группу. Штатные итоговые события
  остаются там. Обработка Telegram новых клиентов не расширяется до автоматической выдачи.
- Подготовить код/миграцию/документы без выкладки и реальных сообщений/панельных
  изменений. Проверки изолировать; PostgreSQL concurrency требует отдельной среды.

## Критерии приёмки

- AC-01: веб без Telegram создаёт собственный renewal с ценой/сроком, повтор
  возвращает активный заказ; выбор/«Я оплатил» не создают Operation.
- AC-02: доверенный admin reply из нужного чата отражается в заказе пользователя;
  сообщение без корреляции, чужой ID/чат/анонимный отправитель отклоняется.
- AC-03: предпросмотр и финальное подтверждение из web/Telegram создают ровно
  одну штатную renewal; истёкший/чужой/изменённый предпросмотр отклоняется.
- AC-04: write-off, конфликт, незавершённая операция/смена владельца блокируют
  выдачу; квоты/UUID/subId/транспорты не меняются, ошибки не подтверждают готовность.
- AC-05: готовность/переписка видны собственному веб-пользователю независимо
  от Telegram; foreign read/POST и CSRF отклоняются, клиент не становится admin.
- AC-06: старые Telegram заказы/подтверждения/уведомления продолжают работать.

## Решение и влияние

PurchaseOrder получает source и nullable contact; активные заказы ограничены
по contact и по user. OrderMessage хранит ручные ответы с ключом идемпотентности,
OrderApproval — краткоживущий предпросмотр с hash условий заказа; восстановление backup отзывает неиспользованные предпросмотры. Notice получает ссылку на заказ и
поля результата Telegram delivery для корреляции ответов. Новые API — собственные
orders/карточка, общие сервисы orders и ограниченные admin handlers.
Миграция 0010 штатная, данные старых заказов сохраняются. Нужны два безопасно
документированных параметра окружения; реальные настройки пока не изменяются.

## Итог и ограничения

Код, штатная миграция, параметры и документация подготовлены. Реальная панель,
мобильные Telegram клиенты и production доставка не проверены. Обычные локальные
базы/службы и стенд не изменялись, реальных сообщений/переводов не было.
PostgreSQL concurrency пропущена в SQLite; unique constraints/row locks требуют
отдельной проверки там. Перед выкладкой проверить активные дубли на аккаунт и
задать реальные ADMIN_TELEGRAM_USER_IDS/ADMIN_TELEGRAM_LOGIN на сервере.

Первая browser-проверка обнаружила SynchronousOnlyOperation: sync Playwright
работает поверх event loop, поэтому ORM в тестовом коде перенесён в отдельный
поток (без DJANGO_ALLOW_ASYNC_UNSAFE). Продуктовый flow не менялся для обхода
проверки. Браузерный повтор прошёл. Финальный повтор admin/API тестов после
устранения второго callback-answer прошёл (26 passed, 1 PostgreSQL skip).

Новые локальные ссылки и индексы UC проверены. Общая проверка launch обнаружила
четыре прежние ссылки на соседний инфраструктурный vpndev, которого нет на этом
macOS checkout; эти исторические ссылки не переадресовывались и не подтверждены.
