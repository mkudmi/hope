# Перенос пользователей и запуск

Дата: 13 октября 2026. План переноса и условия публичного запуска. Локальная реализация завершена. Исторический read-only импорт 33 записей и раскатка standby 12.10 сохранены в [отчёте](research/2026-10-12.md). Текущий production-переход описан в [SDD 0017](sdd/changes/0017-czech-production.md); он не означает, что публичный кабинет или реальный туннель проверены.

## 1. Существующие пользователи 3x-ui

Начать с read-only инвентаризации master: версия API, общий список клиентов, привязки, технические enable/сроки/квоты/автосбросы, идентификаторы подписок, уже записанные Telegram ID. Выгрузку хранить закрыто вне Git. Не читать реестр доступов и персональные конфиги ради проектирования; для импорта они потребуются в защищённой среде.

Разделить реальные клиентские подписки, служебные/диагностические записи и неизвестные записи. AUTO gateway имеет собственного служебного пользователя; его не превращать в клиентский кабинет. Marzban и 3x-ui не синхронизированы автоматически; старые записи Marzban не включать в этот импорт без отдельной миграции.

Дедупликация: прежде всего стабильная сущность master; при старой структуре анализ связей, subId и протокольных секретов. Совпадение отображаемого имени недостаточно. Конфликтный общий subId у разных владельцев требует ручного разбора до приглашения.

Для клиента создаётся внутренний черновик аккаунта без придуманного сервисом пароля и binding с unmanaged-состоянием. Владелец сверяет его с известным человеком. Сроки, квоты, статистика, отключения, секреты и действующие subscription URL сохраняются. Наличие TgID в панели — подсказка, а не подтверждённая новая привязка.

### Рекомендуемая привязка

1. Владелец выбирает проверенную подписку в админке и создаёт приглашение для конкретного человека.
2. Сам передаёт приглашение через прежний личный контакт. Сервис не рассылает приглашения неизвестным владельцам автоматически.
3. Человек открывает браузер, задаёт логин/пароль и сохраняет коды восстановления.
4. Владелец подтверждает активацию существующего доступа после проверки получателя по старому контакту; можно сначала проверить получателя, затем выдавать приглашение.
5. Пользователь связывает Telegram через двустороннее подтверждение в кабинете и боте.
6. Сервис показывает тот же срок и ссылку; пользовательский VPN не требует переимпорта.

Альтернатива для человека, пришедшего в бот без приглашения: создать запрос на привязку → владелец узнаёт клиента через прежний контакт → выдаёт персональное приглашение. Не принимать подписочную ссылку как единственное основание владения.

Знание подписки не даёт право захватить аккаунт: ссылкой могли делиться или она могла утечь. Старые неактивированные пользователи продолжают пользоваться VPN как раньше. Привязка аккаунта к существующей записи не должна сама записывать что-либо в панель.

Повторный импорт идемпотентен по устойчивому ключу панели; не создаёт дубли, новые приглашения и пароли. Изменения между первоначальным снимком и активацией повторно читаются. Клиент включается в автоматическую сверку/применение только после явного принятия под управление владельцем.

## 2. Порядок реализации

| Этап | Результат | Условие перехода |
|---|---|---|
| 1. Подтвердить контракт панели | Read-only адаптер, инвентаризация без секретов в отчётах | Понятна идентичность клиента, сроки, квоты и обновления |
| 2. Учёт аккаунтов | Логин/пароль, приглашения, recovery, аудит, импорт черновиков | Чужой аккаунт/подписка недоступны |
| 3. Кабинет и помощь | Показ сохранённой подписки, инструкции, поддержка | Работает без Telegram и VPN в выбранных сетях |
| 4. Бот и привязка | Общий аккаунт, подтверждение, уведомления | При пересылке/повторе токена нет захвата |
| 5. Ручные операции | Создание и продление через тестовую панель, очередь/сверка | Ретраи/сбои не теряют или удваивают срок |
| 6. Пилот | 2–3 добровольно выбранных клиента, старые ссылки сохранены | Проверены веб, бот, реальные ОС и влияние node-sync |
| 7. Постепенный перенос | Приглашения остальных, мониторинг и восстановление | Нет необъяснённых конфликтов и общих перезапусков |

Первый полезный срез: импорт + браузерный кабинет существующих пользователей + Telegram-привязка, без записи в панель. Это позволяет проверить удобство до подключения технических изменений сроков. Сам продукт запускается полностью только после ручного продления и необходимой проверки отказов.

## 3. Обязательные проверки

| Сценарий | Ожидаемый результат |
|---|---|
| Повтор импорта одного клиента | Один binding, нет новых пользователей панели |
| Несколько транспортов одного клиента | Одна подписка, исходные прикрепления сохранены |
| Служебный пользователь AUTO | Не попадает в приглашения/рассылку |
| Приглашение истекло/отозвано/использовано | Нет активации; владелец может перевыпустить |
| Предпросмотр приглашения мессенджером | GET ничего не активирует |
| Пользователь получил чужую VPN-ссылку | Не получает кабинет или Telegram-привязку владельца |
| Токен Telegram переслан другому | Исходный кабинет должен подтвердить выбранного получателя; чужая привязка не перезаписана |
| Два одновременных bind одного Telegram ID | Одна привязка; второй видит понятный конфликт |
| Потеря Telegram/блокировка бота | Кабинет и VPN продолжают работать |
| Восстановление одноразовым кодом | Новый пароль, отозванные сессии, повтор кода запрещён |
| Неверный логин/код, перебор | Ограничение попыток без раскрытия аккаунтов |
| Подмена Account ID в запросе | Нельзя читать/продлевать чужую подписку |
| Повтор команды «Продлить» | Результат первой операции, без второго добавления |
| Два разных продления из двух вкладок | Проверка версии, повторный предпросмотр второго |
| Продление активного/истёкшего доступа | От текущего окончания/новой даты согласно правилу |
| 31 января + месяц, високосный год | Предсказуемая дата, совпадает с предпросмотром |
| Бессрочность/отрицательный срок панели | Отдельное состояние и ручное решение |
| Исчерпана квота / административная блокировка | Продление не включает доступ неявно |
| Изменился срок через UI панели | Conflict; сервис не перезаписывает его молча |
| API сохранил, но ответ потерян | Read-after-timeout, срок не прибавляется повторно |
| Worker упал после записи API | Возобновление и проверка целевой даты |
| Одна нода не приняла изменение | Partial/alert, без ложного «всё готово» |
| Ошибка hot-apply вызывает restart | Зафиксировано влияние, дальнейшие записи остановлены до разбора |
| Бот выключен на момент окончания | Панель сама прекращает VPN-доступ на всех нужных нодах |
| Старые настройки уже импортированы, подписка истекла | Реальный туннель прекращается, не только выдача ссылки |
| Продление перед очередным напоминанием | Нет устаревшего сообщения о прежнем сроке |
| Сбой Telegram после успешного продления | Срок сохранён, уведомление отдельно повторяется |
| Отказ приложения/его базы | Уже настроенные VPN-клиенты продолжают подключаться до срока |
| Восстановление старого бэкапа HOPE | Записи панели запрещены до сверки новых продлений |
| Смена subId после утечки | Не выдаётся за отзыв уже импортированных протокольных ключей |

Автотесты нужны для сроков, прав доступа, токенов, идемпотентности и отказов интеграции. Ручная проверка нужна для deep links, установки приложений, сетевой доступности кабинета и влияния реального node-sync. Не заменять их проверкой HTTP 200.

## 4. Проверка подключения

Матрица: Android/Happ, iPhone/выбранный клиент, Windows, macOS; Wi-Fi и мобильная сеть минимум двух целевых операторов. Отдельно проверять: открытие кабинета при VPN OFF, вход, получение подписки, установка/import, запуск туннеля, HTTPS-запрос через туннель и выходной IP, альтернативный транспорт, восстановление после истечения/продления.

Результат конкретной сети не обобщать на все. В исследовании RAW проверен, JSON/Clash endpoints оставались 404; не обещать JSON/Clash-импорт до реальной проверки. AUTO TEST не считается подтверждённым основным профилем.

Кабинет без VPN и сами серверы подписок — два разных пути: доступность одного не доказывает доступность другого. Если subscription host заблокирован, кабинет должен дать понятную альтернативу; отдельный резервный endpoint выдачи конфигураций проектируется и проверяется отдельно, без тихой массовой замены старых ссылок.

## 5. Production-операции и возврат

Перед первой реальной операцией проверить зашифрованный backup HOPE, доступность резервных копий 3x-ui и актуальную карточку выбранной подписки. Не выполнять пробные изменения чужой или действующей подписки. Реальная выдача/продление выполняется только по настоящему заказу после ручной сверки владельца; не создавать искусственные заказы или платежи. Проверять PID/ошибки core и действующие подключения до/после операции.

На Czech production real-запись включена только для штатных подтверждённых действий. Локальная среда остаётся write-off. Не включать тестовую рассылку/искусственные Telegram ID на рабочем bot и не применять исторические скрипты research без проверки предусловий.

При проблеме: остановить новые задания записи и пользовательскую рассылку; кабинет оставить доступным с честным состоянием; владелец продолжает обслуживание через панель. После исправления сверить реальные сроки, разобрать каждую pending/partial операцию и только затем продолжить очередь.

При отвязке пилота не удалять клиента 3x-ui. Возвращать только изменённые поля конкретного клиента, учитывая последующие продления; не восстанавливать целый старый dump поверх новых пользователей. Пароли кабинета и приглашения не распространяются на VPN-ключи.

## 6. Критерий готовности

Новый пользователь с приглашением задаёт логин/пароль, получает вручную выданный доступ и подключается по короткой инструкции. Старый пользователь получает кабинет и привязывает Telegram с сохранением прежнего VPN-профиля. При недоступном Telegram он входит через браузер и обращается за продлением/помощью. Владелец одним подтверждением продлевает срок; сервис проверяет применение, показывает ошибку при неполном результате и не удваивает срок на повторах. Резервная копия восстановлена в тестовой среде.

## Экстренный час в production

Программные лимиты и гонки проверены в demo/PostgreSQL; live-применение и туннель остаются непроверенными. На production функция доступна владельцу истёкшей управляемой подписки при заданных правилах, но не должна запускаться ради диагностики на произвольной записи. При включённом техническом клиенте применяется изменение expiryTime; при enable=false пользовательская кнопка не снимает неизвестную блокировку. См. [0002](sdd/changes/0002-emergency-hour.md).

## Пилот полного Telegram-сценария

На текущем компьютере 12.10.2026 запущены Docker web/worker/bot/db с чистой
hope_live: владелец создан, подписок нет, real/write-off. Проверены запуск,
миграции, health и команды Telegram; ответ на настоящий /start проверяет
владелец. Этот запуск не подтверждает чтение панели, выдачу VPN или доставку
в админскую группу. Подробности — [0010](sdd/changes/0010-local-bot-deployment.md).

На изолированном demo проверить нового клиента без браузерного аккаунта: выбранная сумма/срок, личные реквизиты, payment_review без изменения VPN, paid после ручного подтверждения, отдельный предпросмотр выдачи, verified/готовность, копирование своей ссылки, новый браузерный логин и восстановление. Повторить для старой связанной подписки, не выдавая новой вместо неё. Проверить приватность callback и группы.

На устройствах: INCY в российском App Store для iPhone/iPad, оставшийся Happ, Android/Windows/macOS; копирование и импорт одной подписки, обновление, реальный туннель и срок. Read-only локальная интеграция позволяет каталог/заказы/поддержку, не подтверждает серверную выдачу. Бот предупреждает об ожидании ответа владельца до перевода, пока запись выключена.

## Проверка первоначальной настройки владельца

Перед публичным запуском владелец сканирует QR своим TOTP-приложением, подтверждает настройку и проверяет следующий вход по коду. Изолированный browser-тест проверяет отображение и серверное завершение, но не заменяет сканирование на настоящем телефоне. Ручной ключ доступен для настройки на одном устройстве; реальные QR/ключи не включать в скриншоты и отчёты.

## Сервер Чехии: production

Серверная база HOPE остаётся отдельной, локальные данные и записи панели в неё
автоматически не переносятся. По прямому указанию владельца 13.10.2026 Czech
production работает с `PANEL_MODE=real`, записью `PANEL_WRITES_ENABLED=true` и
постоянно запущенными bot/worker. Изменения клиентов выполняются только штатной
ручной операцией владельца; диагностика не пишет в 3x-ui. Раскатка выполняется
вручную через [GitHub Actions](../.github/workflows/deploy-cz.yml) по [SDD 0017](sdd/changes/0017-czech-production.md).
Фактический результат запуска за 13.10: [отчёт deployment](research/2026-10-13.md).
Локальный polling выключают перед cutover. Web пока на loopback 18000; публичный
`/hope/`, создание production-владельца, пользовательская выдача и реальный
туннель требуют отдельной настройки/проверки.
